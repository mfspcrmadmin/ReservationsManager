# Blueprint flow review

The widget loads the booking Blueprint through `blueprint_getbookingblueprint`, renders its transition IDs, and executes `blueprint_executetransition`. The SDK serializes the function arguments as JSON; the transition data is a JSON string inside those arguments. This matches the function's local Deluge signature. Booking and transition IDs remain strings, including the 18-digit IDs from the reported FID Sent failure.

## Findings and local fixes

- Commit `c39ad62` (2026-08-28) replaced the transition dialog with unconditional execution using `{}`. The dialog now opens for editable transition fields; transitions without fields still run directly. Numeric inputs are sent as numbers, booleans as booleans, and blank optional inputs are omitted. Complex requirements such as lookups, attachments, and checklists need the native CRM transition form; the widget explains this instead of submitting them as text.
- Concurrent booking loads could associate an earlier response's Blueprint with a more recently selected booking. Each workspace request now has an ID; outdated requests cannot overwrite the booking or its Blueprint. Clearing the workspace invalidates pending loads.
- Disabling one button was insufficient after a re-render or a click on another transition. Execution now has a shared lock and releases it on success or failure. Dialogs retain their original booking ID, and late execution responses do not refresh a different selected booking.
- The diagnostic parser added during troubleshooting could interpret a `code` inside successful CRM response details as an error. Successful CRM leaf responses are now distinguished from function wrappers, and the tests include the full SDK response envelope.
- Malformed Blueprint loads no longer silently appear as an empty list of transitions. Both local loading function formats remain supported (`success: true` and `error: false`). A partially saved transition is reported as partial rather than completed.

## Server boundary and remaining uncertainty

The logging changes did not change the module, record ID, transition ID, expected state, or data sent by the existing no-field path. The reported `INVALID_DATA` is present in the CRM result; it is not generated by the client.

The local execution source is `_local/crm/blueprints/blueprint_executeTransition`. It reloads the record's Blueprint, checks the current state and available transition, and sends one PUT to the record's `/actions/blueprint` endpoint. No execution-function changes or live transitions were made during this review. Local source is not proof of the version deployed in CRM, and the precise production rejection remains unverified.

There are two local copies of the loading function, under `_local/crm/blueprints` and `_local/crm/crm_functions`, with different return formats. Keep that distinction in mind when comparing the deployed function. Neither should be replaced merely to diagnose this failure.

Tests cover real SDK envelope parsing with mocked transport, exact outgoing arguments, both loading formats, CRM rejection and success, malformed loads, field routing and serialization, concurrent actions, booking changes, partial saves, and out-of-order workspace loads. They do not execute Deluge or reproduce the host's browser environment.

After deploying the widget, verify a suitable transition in CRM and inspect `[Reservations Manager][Blueprint]` if rejected. If transitions with no fields still all fail, inspect the deployed execution function and its original CRM `result`; the restored field dialog alone would not explain that case. Do not infer missing fields from `INVALID_DATA` alone.
