## 4. Decisions made

- All template content, order, wording, criteria, categories and styles must stay data-driven. Never hardcode in JS/Deluge something that belongs in `Templates`, `Template_Sections`, or `Section_Field_Mappings`.
- Do not use Creator for the new reconfirmation system. This means no `Render_Reconfirmation_Template`, no `templatehubconnection`, no `creatorapp.zohopublic.eu` action URLs, and no dependency on Creator helper functions.
- Reconfirmation is not a Communication. It creates `Reconfirmation_Requests`; drafts are created under that module's native `__email_drafts` endpoint.
- Reconfirmation must use the same common CRM template engine where possible (`templ_loadTemplateConfig`, `templ_renderSection`, formatting/replacement/wrapping helpers) but needs its own model builder and renderer because its model hierarchy differs.
- Reconfirmation model must be ported from Creator's `buildReconfirmationModelFromRequest`, not from `drafts_rec_*` or `comm_*` builders.
- Reconfirmation naming: new functions must use `recReq_*`, not `rec_*` or `rec_requests_*`.
- No `recReq_*` fragment function: Creator fragments existed only because large Creator API renders failed. CRM local rendering does not need that workaround.
- Do not change the functions called by the widget until the new `recReq_*` flow is fully tested. Existing local changes in `rec_requests` were premature; remote CRM has not been changed by Codex.
- `SERVICES_MINI_SUMMARY` is deliberately excluded from supplier template migration.

## 6. Important technical constraints

- Deluge `sendmail` requires each allowed sender in a literal separate branch. Do not replace this with a dynamic `from` value.
- `Communications.Render_Model_JSON` is roughly limited to 32,000 chars. Do not store `legacy_model` or complete `service_dates` there for Communications.
- CRM datetime strings such as `2026-07-12T09:20:00+02:00` must be manually parsed by `templ_formatValue`; output is `dd MMM yyyy h:mm AM/PM` / `h:mm AM/PM`.
- Use `apply_patch` for local edits. Preserve unrelated dirty worktree changes.
- Deluge code must be readable: one instruction/concern per line, normal blocks, no dense semicolon-heavy generated code.
- A public supplier action UI replacing Creator Confirm/Issue pages is undecided. Do not invent URLs. The new model may expose `actions.confirm_url` / `actions.issue_url` only once a non-Creator destination is supplied.

## 7. Relevant functions / code

`buildReconfirmationModelFromRequest` (Creator reference)
Purpose: current authoritative reconfirmation model construction.
Inputs: `requestId`, `actions`.
Output: model with `service_dates -> bookings -> steps -> services`, `related_services`, travelers, supplier/contact/user.
Important behavior: loads Request-linked Booking Services; validates relationship; loads Deals, PAX_X_Bookings/PAX, Booking Steps and related services; applies supplier fallback category/subcategory; compacts records.
Dependencies: Creator helper functions only in old implementation; port behavior directly to CRM, do not call it.

`templ_buildReconfirmationModel` (incomplete)
Purpose: should replace the Creator builder.
Inputs: `requestId`, `language`, `actingUserJson`.
Output: CRM-native reconfirmation model.
Important behavior required: standalone CRM loading and compact output; no `drafts_rec_*` dependency.

`templ_renderReconfirmationTemplate` (preliminary)
Purpose: render `RECONFIRMATION_REQUEST` through common CRM section config.
Inputs: `templateCode`, `modelJson`.
Output: `{success, subject, html, template_code}`.
Important behavior: must support Email, Date, Booking, Step, Service, Related_Service and Traveler section contexts and preserve configured order.

`recReq_createRequestsForSelection` (preliminary)
Purpose: future widget entry to group selected services, create Reconfirmation Requests, link services and create a native draft for Email requests.
Inputs: `serviceIds`, `actingUserJson`.
Dependencies: must only call new `functions\templates` functions after refactor.

`recReq_createDraftForRequest` (preliminary)
Purpose: build model, render `RECONFIRMATION_REQUEST`, POST native draft, update request subject/status.
Inputs: `requestId`, `language`.
Endpoint: `/crm/v8/Reconfirmation_Requests/{requestId}/__email_drafts`.

`comm_buildModelsForSelection`
Purpose: Communication-specific builder for Booking/Availability. Do not merge with reconfirmation builder now: it uses compact booking model and `templ_groupServicesByRecipient`, while reconfirmation must preserve a different multi-date/multi-booking hierarchy.

## 12. Important context that must not be lost

The desired reconfirmation model is not the compact Booking/Availability model. Its crucial structure is:

`service_dates[] -> bookings[] -> { booking, travelers[], steps[] } -> { step, services[], related_services[] }`

Creator's model builder contains the exact CRM field reads and fallbacks; port it carefully rather than simplifying it. It is the only accepted behavioral reference.

The old Creator fragment mechanism must not be reintroduced. It only existed to work around Creator render limits.
